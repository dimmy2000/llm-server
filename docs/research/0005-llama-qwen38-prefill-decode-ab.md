# Prefill/decode: Q4_K_M (до 9cc8b22) vs NVFP4-MTP-HIGH (текущий) — A/B замер

Дата замера: 2026-09-12.

Статус: исследование. Сравниваются конфигурации llama-профиля до и после
commit `9cc8b22` (swap на NVFP4-MTP-HIGH с MTP): скорость prefill и decode на
схожих длинах контекста запроса. Изменения конфигурации не коммитились:
`llama/config.yaml` после замера возвращён в состояние HEAD (проверено `git status`).

## Конфигурации

Артефакты — блок `models.qwen3.8-27b` из `llama/config.yaml`, скопирован
посимвольно: старая — `git show 9cc8b22^:llama/config.yaml` (в этой форме
стабильна с `60ab705`), текущая — HEAD. Блоки `filters` (`stripParams`,
`setParamsByID`) идентичны в обеих версиях и на скорость не влияют, поэтому в
артефактах ниже не дублируются (полная версия с режимами — в том же файле
соответствующего коммита).

### Как применить для проверки

Оба GGUF на диске: `/opt/models/Qwen3.8-27B-GGUF/` и
`/opt/models/Qwen3.8-27B-NVFP4-MTP-GGUF/`.

1. **Через llama-swap (так делалось в замерах):** заменить блок `qwen3.8-27b`
   в `llama/config.yaml` на один из артефактов (`${PORT}` — макрос, его
   подставляет llama-swap), затем:
   `docker compose --profile llama restart llama-swap`. Загрузка модели
   ленивая по первому запросу (qwen3.8-27b ~40–60 c).
2. **Стендап-контейнером того же образа (без llama-swap):** заменить `${PORT}`
   на литеральный порт и собрать флаги из артефакта построчно:
   `docker run --gpus all -v /opt/models:/models -p 8080:8080
   ghcr.io/mostlygeek/llama-swap:cuda13 /app/llama-server --host 0.0.0.0
   --port 8080 <флаги из артефакта, кроме строки с ${PORT}>`.

## Методика

- Единый протокол для обеих конфигураций: `POST /v1/chat/completions`,
  model-ID `qwen3.8-27b` (режим с sampling `temperature 0.7`, `top_p 0.8`,
  `top_k 20`, `min_p 0.0`, `presence_penalty 1.5`, `repeat_penalty 1.05`,
  reasoning off — ровно режим из `setParamsByID`), `stream: false`.
- Промпт — разный связный текст под каждый замер (без LCP-переиспользования
  KV между замерами), фактическое число токенов берётся из `print_timing`
  llama-server.
- Метрики: строки `print_timing` llama-server из логов `llama-swap`
  (`prompt eval time` = prefill, `eval time` = decode).
- Переключение: `restart llama-swap` с изменённым `llama/config.yaml`; до
  и после — `git diff` чист (файл в состоянии HEAD).
- Декодирование: `max_tokens 1024/512` (устойчивый decode) и отдельные
  короткие генерации.

## Результаты

### Prefill (промпт-токенов в секунду)

| Промпт (токенов) | Старая Q4_K_M | Текущая NVFP4-MTP |
|---|---|---|
| ~8 000 | 2695 | 1114* |
| ~10 000 | — | 1509* |
| ~15 300 | **2759** | — |
| ~16 200 | **2788** | 2400 / 2065 |
| ~16 900 | **2774** | 2585 |
| ~17 100 | **2776** | 1865 |
| ~28 000 | **2646** | 1390* |
| ~53 300 | — | 1298* |
| ~63 600 | **2117** | 1333* |

`*` — замеры первой сессии текущей конфигурации (во время активной работы
другого потребителя: Firefox/web-сессия на той же машине). Разброс одного и
того же конфига по сессиям 1114–2585 t/s говорит о внешней нагрузке, а не о
свойстве конфигурации. Чистые (пост-restart) замеры обеих конфигураций:
Q4_K_M 2759–2788, NVFP4-MTP 1865–2585.

Вывод: на чистой машине Q4_K_M префилл примерно в 1.2–1.5 раза быстрее на
`~16k` и больше на больших контекстах (2117 vs 1333 на `~63.6k`).

### Decode (генерируемых токенов в секунду)

| Условие | Старая Q4_K_M | Текущая NVFP4-MTP |
|---|---|---|
| ~15–17k контекста, 512–1000 токенов генерации, presence 1.5 | 40.2 / 40.0 / 39.9 (≈**40**) | 54.4 / 54.6 / 56.9 (≈**55**) |
| ~28k / ~63k, 1024 токена, presence 1.5 | 38.1 / 33.2 | 44.1 / 45.0 |
| presence 0.0, ~16.9k, 1000 токенов | 40.0 | 54.6 |
| Короткая детерминированная генерация (50 токенов), presence любой | без MTP ≈ 40 | 142–173 (accept 1.0, mean len 7.0) |

MTP-эффективность в устойчивой генерации скромная: `draft acceptance`
0.67–0.74, `mean len` 2.5–2.9 — далеко от потолка 7 (`--spec-draft-n-max 6`
черновых + 1 токен таргета). Причина — разнообразный текст длинной
генерации, а не presence_penalty: замеры с `presence 0.0` и `presence 1.5`
дали одинаковый accept (0.73 и 0.67–0.74). Несущий фактор — temperature и
предсказуемость текста: при `temperature 0` accept 1.0 и mean len 7.0
(короткие ответы, decode 142–173 t/s), при `temperature 0.7` в длинной
генерации accept ~0.7 на любом presence.

### Итого

- **Prefill: старая конфигурация быстрее** на всех длинах (чистые замеры
  ~1.2–1.6x; на 63.6k до 1.6x).
- **Decode: текущая быстрее** на устойчивой генерации на ~30–40% (55 vs 40
  на ~16k; 45 vs 33–38 на больших), на коротких ответах — в разы.
- На одном «рабочем» запросе (длинный промпт + длинная генерация) разница в
  общем времени определяется весами prefill: сверённый замер `~63k` промпта +
  `1024` генерации — старый конфиг 30.1 + 30.9 = **~61 s**, текущий 47.8 +
  22.8 = **~70 s**.

## Аномалии и оговорки

- Разброс prefill текущего конфига между сессиями (1114–2585 t/s) больше
  межконфиговой разницы на ~16k. Причинно не атрибутирован: вероятнее всего
  внешняя нагрузка GPU (графическая сессия, параллельные потребители), чем
  конфиг. Для бенчмарков с двух GPU + display-сессией нужны повторы в чистой
  сессии.
- Decode текущего конфига чувствителен к предсказуемости текста: 50-токеновые
  предсказуемые ответы дают accept 1.0 (142–173 t/s), длинные — 0.7 (42–55 t/s)
  и на `~63.6k` лучший замер 45 t/s. Цифры «decode скорость» без указания
  accept/mean len недостоверны. Одиночный замер с `presence 0.0` (54.6 t/s,
  accept 0.73) против 44–47 t/s с `presence 1.5` — в пределах шума при
  одинаковом accept; понижать presence ради скорости генерации нельзя без
  контролируемых повторных замеров.
- `--spec-draft-n-max 6` не является лимитирующим: при accept ~0.7 ожидаемая
  длина принятой серии `q/(1-q) ≈ 2.3`, потолок 6 не достигается. Подъём капа
  не ускорит, снижение до 3–4 не замедлит устойчивую генерацию, но потеряет
  headroom коротких предсказуемых ответов (mean len 7.0). Оставлять `6`.
- Внутренние 40 t/s для Q4_K_M из плана `0003` сходятся с замером (40.0) —
  метод согласован.
- Замеры делались с режимом `qwen3.8-27b` (presence 1.5). Для chat/agent
  режимов (presence 0.0) decode NVFP4-MTP выше (54.6), префилл без разницы.

## Подтверждено vs спекуляция

Подтверждено:
- Конфигурации до/после — из git-истории (`9cc8b22` и `9cc8b22^`, стабильно с
  `60ab705`).
- Все цифры — из `print_timing` llama-server (логи `llama-swap`), замер
  2026-09-12.
- Согласованность с `~40 t/s` в плане `0003` для Q4_K_M.

Спекуляция / не подтверждено:
- Причина разброса prefill NVFP4-MTP (1114 vs 2585) — не определена,
  гипотеза — внешняя нагрузка.
- Повторяемость на холодной VRAM/других GPU — не измерялась.
- Влияние `--parallel -1`/`--kv-unified` (4 слота вместо 1) на скорость
  одиночного запроса — не выделено из сравнения.
