# План стабилизации vLLM с Qwen3.8-27B на display-GPU

Дата: 2026-08-16.

Основание: [исследование OOM и перезапусков vLLM](../research/0001-vllm-qwen38-memory-investigation.md).

## Цель

- Сохранить новый публичный model-ID `qwen3.8-27b`.
- Обеспечить стабильную работу vLLM, пока GPU1 одновременно обслуживает
  графическую сессию.
- После получения стабильной базовой конфигурации отдельно определить
  максимально допустимую длину контекста.
- Не маскировать activation OOM увеличением memory budget или настройками KV
  cache, которые не устраняют причину сбоя.

## Принятые ограничения

- Графическая сессия продолжает работать на GPU1 одновременно с vLLM.
- Модель требует обе RTX 5070 Ti и `tensor-parallel-size: 2`; исключить GPU1 из
  vLLM нельзя.
- Старый model-ID `qwen3.8` не сохраняется как дополнительный alias без
  отдельного требования совместимости.
- Базовый профиль настраивается по GPU1 как по устройству с наименьшим запасом
  VRAM.
- Исследовательский отчет остается историческим документом и не
  переписывается под принятые после исследования решения.

## Исходное состояние

- В `vllm/config.yaml` изменение model-ID на `qwen3.8-27b` уже находится в
  index и должно быть сохранено.
- Изменение `max-model-len` с `131072` на `122880` находится отдельно в
  рабочем дереве. Оно не решает runtime OOM, потому что auto-sized KV cache
  продолжает занимать доступный memory budget.
- `README.md` и `AGENTS.md` по-прежнему обещают model-ID `qwen3.8`.
- `README.md`, `AGENTS.md` и `docs/NVIDIA_SETUP.md` содержат устаревшие
  утверждения о безопасности `gpu-memory-utilization: 0.88`, контексте 128K и
  двух активных последовательностях.

## Порядок задач

| Задача | Решаемый вопрос | Зависимость |
|---|---|---|
| 1 | Публичный API-контракт модели | Нет |
| 2 | Корневая причина activation OOM на GPU1 | Задача 1 |
| 3 | Соответствие эксплуатационной документации | Задача 2 |
| 4 | Доказательство стабильности под display-нагрузкой | Задача 3 |
| 5 | Возврат максимально возможного контекста | Задача 4 |
| 6 | Сокращение времени зависшего API после отказа worker | Задача 4 или 5 |

## Задача 1. Зафиксировать model-ID `qwen3.8-27b`

Сохранить в `vllm/config.yaml` единственный публичный ID:

```yaml
served-model-name:
  - qwen3.8-27b
```

Обновить публичный контракт в `README.md` и инструкции для агентов в
`AGENTS.md`. Проверить остальные актуальные файлы репозитория на обращения к
старому ID. Упоминания в исследовательском отчете не менять, поскольку они
описывают состояние на момент диагностики.

В этом репозитории клиентских конфигураций нет. Перенастройка внешних клиентов
на `qwen3.8-27b` является условием развертывания, но не частью изменения этого
репозитория.

Критерии завершения:

- `vllm/config.yaml`, `README.md` и `AGENTS.md` определяют `qwen3.8-27b` как
  единственный публичный ID.
- Актуальная документация больше не обещает поддержку `qwen3.8`.
- После запуска `/v1/models` возвращает `qwen3.8-27b`.
- Короткий запрос с `model: qwen3.8-27b` успешно завершается.

## Задача 2. Ввести безопасную базовую конфигурацию

Заменить текущее неполное изменение `max-model-len: 122880` в
`vllm/config.yaml` следующим набором:

```yaml
max-model-len: 49152
max-num-seqs: 1
max-num-batched-tokens: 1024
enable-chunked-prefill: true

gpu-memory-utilization: 0.85
kv-cache-dtype: fp8
```

Сохранить без изменений:

- `language-model-only: true`;
- `tensor-parallel-size: 2`;
- `no-enable-prefix-caching: true`;
- `no-enable-flashinfer-autotune: true`;
- FP8 KV cache и существующие parser-настройки.

Эта конфигурация решает три составляющие наблюдавшегося сбоя:

- `0.85` освобождает примерно на 0.46 GiB больше физической VRAM, чем `0.88`;
- batch в 1024 токена уменьшает размеры наблюдавшихся failed activation
  allocations примерно в четыре раза;
- одна sequence исключает совместный scheduler-шаг двух запросов, который
  присутствовал при OOM.

На этом этапе не добавлять `enforce-eager`, фиксированный размер KV cache,
allocator tuning, MTP, TurboQuant, prefix caching или FlashInfer autotune. Не
повышать `gpu-memory-utilization`, если startup предложит это для размещения
большего KV cache.

Критерии завершения:

- `docker compose config` принимает итоговую конфигурацию.
- В одном изменении не смешаны дополнительные оптимизации или параметры
  восстановления после сбоя.
- Staged-изменение model-ID не потеряно и не возвращено к старому значению.

## Задача 3. Обновить эксплуатационную документацию

Привести `README.md`, `AGENTS.md` и `docs/NVIDIA_SETUP.md` в соответствие с
безопасной базовой конфигурацией.

Документация должна фиксировать:

- публичный model-ID `qwen3.8-27b`;
- контекст 49152 токена для первого проверяемого профиля;
- `max-num-seqs: 1` и ожидание второго конкурентного запроса в scheduler;
- `max-num-batched-tokens: 1024`;
- `gpu-memory-utilization: 0.85` как настройку для совместной работы с
  графической сессией;
- необходимость сохранять не менее 512 MiB физически свободной памяти GPU1 под
  пиковой нагрузкой;
- запрет повышать utilization только ради прохождения startup-проверки KV.

Удалить устаревшие обещания о безопасном контексте 128K, KV capacity 132578,
двух активных последовательностях и достаточности utilization 0.88.

Критерий завершения: параметры и ограничения во всех трех документах совпадают
с `vllm/config.yaml` и не описывают результаты старого нестабильного запуска как
текущий контракт.

## Задача 4. Проверить базовую конфигурацию под нагрузкой

Перед запуском остановить оба профиля и проверить итоговый Compose:

```bash
docker compose --profile llama --profile vllm down --remove-orphans
docker compose config
docker compose --profile vllm up -d --wait --wait-timeout 1800
```

Проверить startup и состояние контейнера без фильтрации логов:

```bash
docker compose --profile vllm logs vllm-server
docker inspect --format 'restart={{.RestartCount}} oom={{.State.OOMKilled}} status={{.State.Status}} health={{.State.Health.Status}}' vllm-server
nvidia-smi --query-gpu=index,name,memory.total,memory.used,memory.free,display_active --format=csv
```

Проверить API:

```bash
curl --fail http://localhost:8080/health
curl --fail http://localhost:8080/v1/models
```

Нагрузочную проверку выполнять при обычной графической сессии и открытых
типичных GPU-приложениях. Сначала отправить один streaming-запрос с prompt около
12718 токенов и `max_tokens=32000`, затем два таких запроса одновременно. При
`max-num-seqs: 1` второй запрос должен ожидать scheduler. HTTP 200 без
завершающего `[DONE]` не считается успешным результатом.

Критерии завершения:

- Первый cold start завершается без дополнительного автоматического restart.
- `GPU KV cache size` не меньше `max-model-len`.
- `/v1/models` публикует `qwen3.8-27b`.
- Одиночный и оба конкурентных streaming-запроса завершаются `[DONE]`.
- На GPU1 под пиковой нагрузкой остается не менее 512 MiB физически свободной
  памяти.
- В логах нет `torch.OutOfMemoryError`, `EngineDeadError`, RPC timeout и
  повторяющихся `No available shared memory broadcast block`.
- `/health` остается успешным, а throughput не зависает на нуле при
  `Running > 0`.
- `RestartCount` не меняется минимум 30 минут нагрузки и во время длинного
  ответа.

Если 49152 не проходит startup-проверку минимального KV cache, снизить только
`max-model-len` до 32768 и повторить весь тест. Не повышать utilization. Если
возникает runtime OOM или не выдерживается запас 512 MiB, задачу не считать
завершенной и не переходить к расширению контекста.

## Задача 5. Определить максимальный стабильный контекст

После успешной проверки базового профиля повышать только `max-model-len` по
одному шагу:

```text
49152 -> 65536 -> 98304
```

На каждом шаге сохранять `max-num-seqs: 1`, `max-num-batched-tokens: 1024` и
`gpu-memory-utilization: 0.85`, выполнять новый cold start и повторять критерии
задачи 4. В проекте оставить максимальную длину, прошедшую startup и нагрузочный
тест, после чего обновить числовые значения в документации.

Не возвращать `max-num-seqs: 2` в рамках этой задачи. Параллелизм должен быть
отдельным экспериментом после выбора длины контекста.

Если контекст 122880 станет обязательным требованием, создать отдельную задачу
на проверку следующего профиля:

```yaml
max-model-len: 122880
max-num-seqs: 1
max-num-batched-tokens: 1024
gpu-memory-utilization: 0.85
enforce-eager: true
```

Этот вариант не входит в базовое исправление и может быть отклонен startup из-за
недостаточного KV cache.

## Задача 6. Сократить задержку обнаружения мертвого worker

Выполнять только после стабилизации memory profile. Сначала измерить
максимальную длительность нормального scheduler iteration, включая первый
compile и длинный prefill. Если измеренный запас достаточен, добавить в
`vllm/docker-compose.yaml`:

```yaml
environment:
  VLLM_EXECUTE_MODEL_TIMEOUT_SECONDS: "120"
```

Повторить cold start и длинный streaming-тест, чтобы исключить ложный timeout.
Это изменение сокращает период зависшего API после отказа worker, но не является
исправлением OOM.

Не менять только `healthcheck.retries` в ожидании автоматического restart:
Docker healthcheck сам по себе не перезапускает работающий контейнер, а
`/health` остается успешным до того, как vLLM пометит engine мертвым. Внешний
watchdog является отдельной задачей и нужен только при явном требовании к SLA.

## Итоговые критерии

План завершен, когда:

- единственный публичный model-ID равен `qwen3.8-27b`;
- выбран и задокументирован максимальный проверенный context limit;
- vLLM стабильно работает при одновременной графической нагрузке GPU1;
- под пиковой нагрузкой сохраняется не менее 512 MiB свободной VRAM GPU1;
- два одновременно отправленных запроса завершаются без совместного выполнения
  двух sequences и без OOM;
- контейнер не перезапускается минимум 30 минут нагрузочного теста;
- конфигурация и актуальная документация не содержат старых неподтвержденных
  обещаний о 128K, двух sequences или безопасности utilization 0.88.
