# 10 — Вытеснение device-state слотов при нескольких удерживаемых диалогах

Type: task
Status: resolved

## Question

`--device-state-slots 4` при `--host-state-slots 0` и `--host-kv-mib 0`
(обязательные значения на tp2) означает, что удерживаемые диалоги живут
только в device-state слотах: при пятом диалоге самый старый вытесняется, и его
следующий turn префиллится заново. Проверить:

- пять последовательных диалогов по два turn каждый — каждый должен вернуть
  корректный ответ, без OOM и без порчи ответа после вытеснения;
- поведение вытесненного диалога: растёт ли `prompt_tokens` второго turn
  обратно до полной длины истории (признак повторного префилла);
- не появляется ли в логе ошибок 4xx/5xx и не падает ли CUDA graph;
- время второго turn вытесненного диалога против такого же без вытеснения.

Побочно: тем же прогоном проверить, что два диалога в разных слотах
не мешают друг другу (VRAM не растёт, ответы не смешиваются).

## Acceptance

- Пять диалогов подряд отработали, ни один не упал.
- Зафиксировано, что происходит со вторым turn вытесненного диалога: повторный
  префилл с ростом `prompt_tokens` или ошибка.
- Результат записан в тикет и, если требуется поправка профиля, в
  `docs/research/0009-ninfer-tp2-two-5070ti.md` и в `ninfer/config.yaml`.

## Answer

Проверено 2026-10-05 на профиле `ninfer` с `--device-state-slots 4`,
`--host-state-slots 0`, `--host-kv-mib 0`. Ни одного OOM, ни одной ошибки
движка за весь прогон; `/health` — 200; свободная VRAM после всех прогонов
2016 MiB на GPU0 и 1501 MiB на GPU1.

Восемь сессий по ~11.6k токенов, перемежающиеся возвраты к каждой: все ответы
корректны, ошибок нет. Собственно удержание состояния видно по
`cached_tokens`, а не по `prompt_tokens` (последний включает историю,
пересланную клиентом, и поэтому растёт всегда).

Удержано ровно **3 сессии из любого числа** (3 из 4, 3 из 5, 3 из 6, 3 из 7,
3 из 8, стабильно в двух раундах), то есть `device-state-slots 4` =
3 удерживаемых диалога плюс один слот под текущий приватный continuation
текущего запроса. Удержанные сессии отвечают за 0.13–0.17 с против 2.4 с с
полного префилла (≈11.6k токенов), то есть выигрыш примерно 18× по TTFT.
Вытесненные сессии не падают и не портят ответ — они просто префилятся заново.

Дополнительно: одиночная сессия сохраняет состояние даже через шесть
посторонних запросов между turn'ами, если возврат происходит сразу после них
(TTFT 0.1 с против 20.5 с на премиссе 75k); при возврате в середину длинной
череди посторонних запросов состояние уже вытеснено. То есть число удерживаемых
диалогов важнее длины паузы между turn'ами.

Практический вывод для потребителей: одновременно живых диалогов с
переиспользованием состояния должно быть не больше трёх; четвёртый и дальше
получат полный префилл, но останутся корректными. Увеличение
`--device-state-slots` не проверялось — на этой машине запас VRAM есть
(1501 MiB на GPU1), но каждый слот — это ещё один StateImage.

Изменений в `ninfer/config.yaml` не требуется.
