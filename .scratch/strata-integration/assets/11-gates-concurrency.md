## RAM-гейты / fail-fast (memory hog 20 ГиБ на хосте)

Фунд — python, 312 × 64 MiB блоков, трогается постранично; после подъёма
MemAvailable = 34.6 ГиБ (пороги гейтов: iq3 — 46 ГиБ = 48234496 KiB,
iq2 — 36 ГиБ = 37748736 KiB). Резидентный NInfer ко второму запросу был
выгружен стандартной механикой свапа (Mid-снапшот: VRAM опустошена
15919/14769 MiB free) — llama-swap выгружает старые бэкенды ДО старта
нового процесса через cmd.

| запрос | HTTP | wall | запись в логе контейнера |
|---|---|---|---|
| strata-iq3 (max_tokens 8) | **500** | **2.15 с** | `strata: RAM gate: need 46GiB, MemAvailable 35912MiB — резидентный бэкенд не выгружен или память занята посторонними` → `group: starting strata-iq3 failed: upstream command exited prematurely` |
| strata-iq2 (max_tokens 8) | **500** | **0.27 с** | `strata: RAM gate: need 36GiB, MemAvailable 35909MiB — ...` → то же |

- Отказ произошёл ровно при доступе ниже порога, мгновенно, с причиной в
  логах; ретраев нет (fail fast). 500 клиенту — унифицированная ошибка
  llama-swap `upstream command exited prematurely`, точная причина — в
  логах контейнера (как и предполагали в 08).
- Разница стен: 2.15 с платят выгрузку резидентного NInfer (page-locked),
  0.27 с — чистый гейт без выгрузки.
- Восстановление: фунд убит → обычный запрос `qwen3.8-27b` → HTTP 200
  (cold NInfer 7.42 с) — автомат вернулся в рабочее состояние без ручных
  шагов; затем повторно прогнаны циклы с полными замерами.

## Конкурентность (запрос к другому ID во время идущего свапа)

Проба 1: запрос `strata-iq3` (cold с резидентного NInfer) → на +4 с
параллельный запрос к `qwen3.8-27b`. Проба 2: запрос `strata-iq2` →
параллельный запрос к `strata-iq3` на фоне незавершённого свапа.

- Все запросы — **HTTP 200**, отказов нет; клиент просто ЖДЁТ.
- Проба 1: qwen-запрос получил ответ за 22.6 с = 4 с ожидания + досиживание
  свапа iq3 (его chain 18.5 с) + собственная смена (unload iq3 → старт
  NInfer; движко-лог: `starting engine` 06:50:44.8 → engine ready total 7.2 с
  в 06:50:51.97 → ответ 06:50:52.1).
- Проба 2: iq3-запрос — 200 за 15.79 с (смена пришла сразу после
  возвращения первого запроса); инициатор iq2 — 200 за 28.95 с (досидел
  очередь из двух смен).

**Зафиксированный факт:** llama-swap v265 с дефолтной exclusive-группой
сериализует смены строго FIFO по прибытии; параллельного удержания двух
тяжёлых бэкендов нет — во всех 12+ cold-loads сессии движко-лог показывает
`stopping` старого движения (	strata-шейдауна) до `starting engine`
следующего (строки переплетены в docker logs, сырьё: 11-concurrency.logjsonl
и логи контейнера 06:50:28–06:51:30). Для клиента запрос к «другому» ID на
фоне свапа — просто дороже (22–29 с в худшем чейне), но никогда не отказ.
